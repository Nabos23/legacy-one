Knowledge Base Architecture

A scoped, hybrid retrieval layer on Qdrant Cloud: org, user, and agent-level Knowledge Bases sharing one collection.

one-page summary, for presenting

The whole thing, in one page

A document gets uploaded, chunked, and stored once. A question gets cleaned up, searched against three tiers at once (company, personal, agent), combined into one ranked list, permission-checked, and handed to the AI. Every stage below has a full diagram further down this page.

One database, many tenants

Every company, KB, and document lives in the same database, kept apart by tags, not separate databases.

Ingestion

Upload a document, split it into small chunks, turn each into two searchable fingerprints, and save.

Query rephrase

Clean up the question using recent chat, so "it" and "that" get resolved before searching.

Query embedding

Turn the question into the same two fingerprints used for documents: one for meaning, one for keywords.

Hybrid search

Search with both fingerprints at once, scoped to just this tier's documents, in a single database call.

Graph expand

If turned on for that tier, also pull in chunks linked to the ones already found.

Merge + rerank

Combine the ranked results from company, personal, and agent search into one list.

Scope filter

Check permissions one more time and drop anything this person isn't allowed to see.

Agent context

Hand the safe, ranked results to the AI as part of the conversation, and save them for later turns too.

Frontend

Reuses existing upload, permission, and connect-to-agent screens. New: a KB manager and showing sources in chat.

Overview

A Knowledge Base is owned at one of three tiers (organization, user, or agent), and each tier runs retrieval with its own settings. Documents land in one shared Qdrant collection, differentiated by payload rather than by separate collections. A query is rephrased, searched per tier, merged, and permission-filtered before it reaches the agent.

Complete architecture

How Qdrant tells multiple KBs and documents apart

One org can have many Knowledge Bases, and one KB can have many documents. All of it lives in the single kb_chunks collection above, with no collection-per-org or collection-per-KB. Differentiation is entirely by payload field and index, the same mechanism already running today for DB-schema search (ai/rag/schema_indexer.py), one level deeper: org_id as the tenant index, kb_id as a keyword index (many per org), doc_id as a keyword index (many per KB).

Ingestion pipeline in detail

The four-box ingest row in the diagram above compresses ten real steps. Reused pieces are cited to the file that already does them; everything else is new.

Query rephrase in detail

Nothing in this codebase rephrases a query today: the reuse table already flags this as net new. What exists is the shape a rephrase step would reuse, the same last-3-turns-of-history pattern MainAgent._route already uses for follow-up-aware routing (ai/agents/main_agent.py:118-121), and the same litellm call wrapper (:125-130).

Query embedding in detail

Dense query embedding already exists, in get_relevant_schema_sync: a plain litellm.embedding call on the same settings.EMBEDDING_MODEL used for indexing (ai/rag/schema_retriever.py:114-124). Sparse query embedding does not: I checked whether the installed qdrant-client's optional sparse-embedding helper is available, and it is not. qdrant_client.models.SparseTextEmbedding resolves to None at runtime because it depends on the fastembed package, which is not a dependency of this project (absent from pyproject.toml and uv.lock).

Hybrid search in detail

Today's search inside a tier's KB would be a single dense-only query_points call, the same shape get_relevant_schema_sync already makes (ai/rag/schema_retriever.py). Hybrid search adds a second, sparse vector and fuses both in one call, using capability already present in the installed qdrant-client, confirmed by inspecting qdrant_client.models directly: Prefetch, FusionQuery, Fusion.RRF.

Graph expand in detail

This runs inside each tier's hybrid-search lane, using the links Build chunk links wrote at ingest time. The pull is a direct point lookup by id (QdrantClient.retrieve, confirmed on the installed client), not another similarity search.

Merge + rerank in detail

Each tier lane already returns a ranked list: its own dense and sparse results fused with Qdrant's Fusion.RRF inside that lane's single query_points call. Merge + rerank is what happens next: three independently-ranked lists, from three separate filtered Qdrant calls, need to become one.

Scope filter in detail

This is not a new rule: it's the exact visibility check agents already use, applied to chunks instead of agents. build_agent_visibility_clauses in backend/agent/services.py:562-589 is the single visibility rule for the whole app today (reused as-is by chat, direct_agent, and widget code); a KB's owner_scope would be checked the same way.

Agent context in detail

This is also not new machinery: it's the exact path search_schema already uses today, read directly from ai/agents/sub_agent.py and ai/rag/schema_retriever.py. A KB retrieval tool would return a plain string the same way and travel the same route into the model.

Staying reliable and scalable, not just correct on paper

  1. Ingestion must be a background task, not an inline request. Chunking + dual embedding + link-building for a large document can't run inside the upload HTTP request. Reuse the exact pattern backend/dbconnection/services.py already uses for schema indexing: asyncio.create_task(...) fires the pipeline, the request returns immediately (:453-455), and a status flag gets set on completion (schema_indexed: True at :397, would be kb_document_indexed here). This isn't shown anywhere above and needs to be.
  2. A failed lane shouldn't fail the query. If one tier's Qdrant call errors or times out, merge + rerank should proceed with whichever lanes succeeded, the same discipline get_relevant_schema_sync already follows: catch, log, degrade, never crash the agent turn over a search failure (schema_retriever.py:133-135). This isn't in the pipeline diagrams above and should be, wherever hybrid search is actually implemented.
  3. One collection scales by tenant count, not by row count. org_id as a tenant index plus a per-tenant HNSW subgraph (payload_m) is Qdrant's own recommended pattern for many tenants sharing one collection, already proven at production scale on schema_tables. kb_chunks inherits that property directly; adding more orgs, KBs, or documents doesn't change the shape of the solution.
  4. Sparse search is additive, not a blocker. Until a sparse encoder is chosen (section 06's open item), hybrid search's Prefetch list can run dense-only, the exact single-vector shape schema RAG already runs in production today. This ships in a dense-only phase first rather than waiting on the missing piece.
  5. Delete-then-upsert has a real, inherited gap. Re-ingesting a document briefly leaves zero points for it between the delete and the upsert, the same behavior schema_indexer.py already has for DB schemas today. That's been fine at schema scale (dozens of tables); at document scale, a single doc can be thousands of chunks, so that window gets longer and is worth re-checking before assuming it carries over unchanged.
